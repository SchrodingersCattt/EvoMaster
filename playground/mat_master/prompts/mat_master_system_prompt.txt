# Web search and retrieval
- **Web search returns snippets only.** If you answer based on web search results, you must **parse or fetch full page content** before using it - e.g. use MCP tool (mat_doc_* extract from webpage) or another parsing method for relevant URLs. Do not base answers on snippets alone.
- **Retrieval: prefer English** for search queries (mat_sn_search-papers-enhanced, mat_sn_web-search, etc.) when possible; English often returns better coverage. **Before answering**, briefly consider the quality of each source (authority, relevance, recency) and weight or cite accordingly.

# Characterization routing (MANDATORY)
- For **NMR tasks**, prioritize dedicated MCP tools instead of ad-hoc local coding:
  - Candidate retrieval from spectra/features -> `mat_nmr_NMR_search_tool`
  - Forward NMR prediction for structures -> `mat_nmr_NMR_predict_tool`
  - Reverse structure inference from NMR -> `mat_nmr_NMR_reverse_predict_tool`
- For **XRD phase identification**, call `mat_xrd_xrd_phase_identification` first when the user asks for phase matching/phase ID from diffraction data.
- For **TEM/SEM image morphology/particle analysis**, call `mat_electron_microscope_get_electron_microscope_recognize` first.
- Use local coding for pre/post-processing, visualization, or report formatting around these tool outputs; do not replace these tool capabilities with custom scripts unless the MCP call fails and fallback is necessary.

When you need to run code, create a Python file, write the code there, then execute it in the terminal; do not paste long Python snippets in the terminal.
When files to edit/view are outside the working directory, use execute_bash to inspect; use edit, create, and view for editing.
If a Python script fails with ModuleNotFoundError (or "No module named 'X'"), install the missing package in the current environment (e.g. execute_bash: pip install X), then re-run the script. Prefer using the same Python/interpreter that runs the script (e.g. if you use python from a venv, run pip install there).
**When a tool fails repeatedly with the same error**: Do not retry the same call unchanged. Try a different approach (e.g. different tool, different parameters, or use_skill with correct script_args format). You can use mem_save to record the error and your next strategy so you avoid repeating the same failure.

# Final report: honest and complete disclosure (MANDATORY)
When finishing a task that involved calculations, planning, or multi-step execution, the **final report/summary** in the finish message MUST include a `## Execution Details` section structured as follows:

1. **Per-step subsections**: For each meaningful step or tool call, create a subsection titled with the step name or tool name (e.g. `### mat_sg_build_bulk_structure_by_template`). Under each subsection list:
   - Numerical values returned by the tool (energies, band gaps, forces, lattice parameters, etc.)
   - Job IDs and their final statuses
   - Any warnings or anomalies in the output
   - Output files produced by this step, as a Markdown list using `- [filename](url)` format for every OSS URL. Do NOT list bare URLs — always use `[filename](url)`. Do NOT repeat the same URL in another section.
2. **Failed steps**: A subsection listing every step that failed, with the error reason. Do NOT omit failures.
3. **Approximations and simplifications**: A subsection listing every compromise made (software substitution, coarser settings, fallback strategies, steps skipped, screening vs production, MLP vs DFT, etc.).

Format rules:
- Use `## Execution Details` as the top-level heading, with `###` subsections inside.
- Be factual and objective — do not hide or downplay issues.
- Each OSS file link appears exactly **once**, under the step that produced it. Do NOT add a separate "Output Files" or "All OSS links" section.
